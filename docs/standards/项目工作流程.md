# 项目工作流程

- `feature.md` 是项目功能状态的唯一事实来源。
- 任何新增、完成、变更、弃用或移除功能的修改，都必须在同一个提交中更新 `feature.md`。
- 每个功能条目只使用一句话描述，并明确标注复选框状态。
- 如果无法用一句话准确描述某项功能，应在 `docs/` 下新增或更新一份聚焦该功能的文档，并在 `feature.md` 的对应条目中添加链接。
- 只有在实现及相关测试均完成后，才能将功能标记为已完成。
- 不要单独创建 `todo.md`；待办功能统一记录在 `feature.md` 中。
- 每次执行 Git 提交前，必须确认本次提交实际使用的作者姓名和邮箱，且作者邮箱必须以 `@xunlei.com` 结尾；如果当前仓库没有已经配置的 `@xunlei.com` 提交身份，必须停止提交并询问用户姓名和邮箱，收到确认后使用 `git config --local --add user.name <姓名>` 和 `git config --local --add user.email <邮箱>` 保存到项目 Git 配置，再重新确认实际提交身份。
- 只有在用户当前请求中明确要求执行 `push` 或“推送”时，才允许执行 Git 推送；完成修改、测试、提交、拉取或变基均不构成隐含的推送授权。
- 每次执行 Git 推送前，必须先拉取目标远端分支的最新内容：如果没有尚未发布的本地提交，则仅允许快进更新；如果存在尚未发布的本地提交，则将这些提交变基到更新后的目标分支上。
- 完成上述拉取或变基后、推送前，必须检查最终工作区、提交历史和相关差异，并运行与改动范围相匹配的检查；仅在不存在未解决冲突或已发现的回归问题时才能推送。
- 每次执行 Git 推送前，必须在上述拉取或变基后的最终提交上完成与 CI 一致的格式检查、Clippy、Release 全量测试和 Release 生产构建，全部通过后才能推送；测试通过不能替代生产构建通过。
- 每次创建或推送 Git tag 前，必须切换到 `master`，以仅快进方式同步最新 `origin/master`，确认工作区干净且本地 `HEAD` 与 `origin/master` 完全一致；tag 只能指向该 `master` 提交，禁止在功能分支、修复分支或尚未合入 `master` 的提交上创建或推送 tag，不满足任一条件时必须停止。

## 需求对齐门禁

- 当请求要求在开发前提供方案或完成方案对齐时，必须将这一顺序视为强制实现门禁：首先记录需求、兼容性基线、范围、非目标和验收标准；然后提供技术设计、受影响文件、性能影响、数据面开发约束情况、风险和验证计划；等待用户明确确认后，才可以修改实现、依赖、配置或生成产物。
- 在需求和技术设计对齐期间，仓库改动仅限于用户要求的规划或流程文档，以及 `feature.md` 中对应的待完成条目；不得隐式开始实现。
- 如果实现将实质性偏离已确认的需求或设计，必须停止实现并返回对齐阶段，确认后再继续。

## 数据面开发约束

- 热路径必须可预测：单包处理必须短、非阻塞且成本有界，避免外部 I/O、无界遍历及不必要的分配和复制。
- 状态归属必须清晰：高频可变状态必须有唯一所有者；跨模块优先使用消息、原子值或不可变快照，避免共享大锁。
- 资源与退化必须有界：队列、缓存、连接和单轮工作量必须设置硬上限；过载时快速失败，并明确丢弃、拒绝或回退语义。
- 集合操作必须有界：数据面不得全量扫描随用户、连接或流量规模增长的集合，包括 `HashMap`、LRU 和会话表等；查找、过期、清理、统计和淘汰必须通过索引、分片、桶或时间轮、游标分批等结构实现，并限制单包及单轮扫描量。
- 旁路不得干扰主流程：统计、调试、配置和上报不得阻塞数据面，也不得改变业务处理结果。
- 性能变更必须可验证：涉及热路径、并发、线程或容量的修改，必须说明成本与失败语义，并验证吞吐、CPU、内存、队列、丢弃和尾延迟。
- 数据面改动的代码评审必须确认：状态由谁拥有，单包和单轮的最坏成本是否有界，下游变慢时如何退化，是否存在阻塞或持锁等待，是否扫描随业务规模增长的集合，以及是否有性能回归证据。
