## 环境就绪后的顺序

1. 安装与选定平台匹配的 Flutter、Rust 和平台 SDK，确认版本及依赖约束，执行 `flutter doctor -v`。
2. 在有权限且明确核心版本的前提下，将核心源码准备到 `native/`，阅读其规范，核对 workspace、features 和 ABI；本次未获取该仓库。
3. 依照目标工作流编译原生库并生成对应头文件，核对输出架构；Android 使用 cargo-ndk，Apple/Linux/Windows 使用对应 target 和 cbindgen，OpenHarmony 使用其独立工具链。
4. 按现有构建逻辑执行 `cp ci/version.code.txt lib/assets/version.txt`，随后执行 `flutter pub get`；依赖解析失败时保留诊断并停止，不跳过版本约束。
5. 执行快速检查和受影响平台的 Release 构建，再完成必要的集成和性能验收。

## Flutter 快速检查

在仓库根目录、环境就绪后执行：

```sh
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test --timeout 60s
```

如使用 FVM，则为命令分别添加 `fvm` 前缀，并核对实际使用的 Dart/Flutter 来自同一 SDK；这些命令不修改源代码格式，历史格式或静态错误应记录，不能夹带全仓格式化。

当前 widget 测试仍为不匹配应用的计数器模板，需要经方案确认后补充真实测试；不能删除断言或忽略失败来宣称门禁通过。

## 原生与生产构建

| 平台 | 原生准备（参照现有工作流） | Flutter Release 构建 |
| --- | --- | --- |
| Android | `native/jmbackend/platforms/android` 使用 cargo-ndk，将库输出到 `android/app/src/main/jniLibs` | `flutter build apk --release --target-platform android-arm64`（其他 ABI 分别验证） |
| iOS | 使用 `platforms/ios` 的 Cargo 清单，复制 `librust.a` 并生成 `ios/rust.h` | `flutter build ios --no-simulator --no-codesign --release` |
| macOS | 使用 `platforms/macos` 分别构建 x86_64/aarch64 并通过 lipo 合并到 `macos/librust.a`，生成 `macos/rust.h` | `flutter build macos --release` |
| Windows | 使用 `platforms/windows` 构建 `x86_64-pc-windows-msvc`，复制 `rust.lib` 并生成 `windows/rust.h` | `flutter build windows --release` |
| Linux | 使用 `platforms/linux` 构建 x86_64 库并生成 `linux/rust.h`、`linux/rust1.h` | `flutter build linux --release` |
| OpenHarmony | 专用 Flutter/SDK、Rust OHOS target、`make` 和原生库同步，以及工作流中的依赖/图片实现替换 | `flutter build hap --target-platform=ohos-arm64`，随后在 `ohos/` 执行 `hvigorw assembleHap --release` |

每个平台应在对应受支持主机或工作流环境验证，iOS 无签名构建和 OpenHarmony unsigned HAP 不能等同于可正式分发的签名制品；本地 Release 构建仅用于验证，生产发布制品必须遵守团队 Tag CI 规则。

Rust 门禁需在取得核心源码并确认清单后执行 `cargo fmt --check`、`cargo clippy`、`cargo test --release`、`cargo build --release`，结合该核心实际 workspace、all-targets、features、target 和生产路径补全参数；这里不提供猜测的全量测试命令，未知或缺失核心检查属于阻断条件。

## 测试覆盖计划

| 范围 | 所需场景 |
| --- | --- |
| 数据模型与通道 | 正常 JSON、缺失字段、错误响应、异常类型、跨版本兼容，使用脱敏固定样例 |
| 初始化与登录 | 成功、未登录、失败、身份验证、初始化期间页面销毁，mock MethodChannel 隔离真实账号 |
| 搜索与阅读 | 空结果、分页、章节边界、图片失败、方向/缩放/翻页、阅读进度恢复 |
| 下载与导入导出 | 并发上限、取消和重试、权限拒绝、无效文件、磁盘不足、中断恢复与清理 |
| WebDAV | 合并冲突、超时、失败、重复触发、覆盖确认与测试数据隔离 |
| 平台集成 | 目标平台 ABI、原生库加载、通道调用、文件权限、窗口与生命周期 |
| 性能 | 长章节预加载、批量下载、慢网络下 CPU/内存/队列/失败率及 P95/P99 |

以上是验证计划，实施和测试补充须另行对齐；统一测试入口仍需补齐总超时、环境隔离、自动清理和失败诊断，目前不能声称已经具备一键完整验收。

## 合并、发布与回退

遵守 [AGENTS.md](../AGENTS.md) 及团队规范：修改在功能/修复分支经 PR 合入 `master`，各操作分别取得授权，提交身份须满足公司邮箱要求；GitHub SSH 登录成功不等于提交身份已合规。

现有 Release 工作流仅手动触发，并存在自动创建 Release 和覆盖资产逻辑，不能作为团队要求已落地的依据；整改需包含 Tag 触发、客户端与核心 SHA、工具链和 Pipeline ID 记录、不可覆盖制品以及发布人确认。

涉及实现的后续变更，应按“构建环境与版本方案 → 业务测试 → CI 门禁 → 发布约束”拆分独立变更意图，均需先评审方案；发布观察人、停止阈值、灰度与回退 Tag 尚未指定，不得自动发布，回退只使用历史 Tag 对应原始制品。
