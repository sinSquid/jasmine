# 团队与 AI Coding 项目规范

> 状态：初稿
>
> 目标：统一团队成员与 AI Coding 的研发行为，通过需求、方案、测试、评审、发布和验证门禁减少线上事故。
>
> **标识说明：加粗内容表示必须有人介入确认、评审、批准或操作，AI 不得独立决定或越过。**
>
> 人员执行入口：[团队成员研发执行规范](<团队成员研发执行规范.md>)

## 1. 基本原则

- 人员和 AI 均必须遵守本规范。
- AI 可以辅助分析、设计、编码和测试，但**不能替代需求确认人、评审人和发布责任人**。
- 未满足门禁时必须停止进入下一阶段，不得以赶进度为由绕过。
- 必须如实区分已修改、已测试、已评审、已提交、已发布和已完成线上验证；未实际执行的操作不得描述为已完成。

### 1.1 项目级 `AGENTS.md`

- 每个项目必须在仓库根目录维护 `AGENTS.md`，作为人员和 AI 开始工作前必须阅读的项目级执行入口。
- `AGENTS.md` 必须说明项目特有的构建、测试和检查命令，Git 分支、提交、推送和 Tag 约束，以及架构、性能、安全等专项约束和停止条件。
- `AGENTS.md` 用于补充和具体化本规范，不得降低或绕过本规范的门禁；项目规则更严格时执行更严格的规则，**存在歧义或冲突时必须先停止并由相关人员完成对齐**。
- `AGENTS.md` 只保留项目特有内容，通用规则应引用本规范而不应整段复制；项目工作流变更时必须同步更新。

## 2. 标准研发流程

1. **开发与需求提出人完成需求对齐**
2. **AI 提供技术方案，由参与实现的开发人员人工评审，并明确确认与需求一致**
3. 编码与自动测试
4. **开发人员触发 AI 基于实际差异进行 Review，并确认影响范围和风险**
5. CI 门禁
6. **非作者人工评审**
7. 合入主分支
8. **发布人员创建 Tag**
9. Tag CI 构建制品
10. **发布人员执行灰度发布和线上验证**

## 3. 需求对齐后再开发

开发前必须明确：

- 目标、范围和非目标；
- 兼容性要求；
- 验收标准；
- 负责人和风险等级。

**需求存在歧义、缺失或冲突时必须先与需求提出人确认**，禁止人员或 AI 自行猜测。需求未对齐前，只允许编写或修改需求、方案等规划文档，不得开始修改实现、依赖、配置或生成发布制品。

## 4. 技术方案确认后再编码

技术方案至少包含：

- 实现思路和影响文件；
- 接口、配置、数据及上下游影响；
- 兼容、异常、失败和降级策略；
- 资源上限及性能影响；
- 测试、灰度、监控和回滚方案。
- 提交拆分和实施顺序；如需前置重构，必须单独说明重构目的、范围和验证方式。

AI 提供的技术方案必须由参与实现的开发人员人工评审。**只有开发人员明确确认方案与需求一致并同意开始开发后，AI 才能开始编码**；沉默、继续讨论或只确认局部内容均不视为授权。实施过程中需要实质性偏离已确认方案时，AI 必须停止开发并说明偏离内容，**等待开发人员重新对齐并明确确认后**才能继续。

## 5. 控制变更范围

- 只修改当前需求涉及的内容。
- 禁止夹带无关重构、依赖升级或大范围格式化。
- 发现额外问题时应单独记录、**单独评审**和单独实施。
- 接口说明和运维文档必须与代码在同一变更中更新。

### 5.1 功能状态管理

- `feature.md` 是项目功能状态的唯一事实来源。
- 任何新增、完成、变更、弃用或移除功能的修改，都必须在同一个 Commit 中更新 `feature.md`。
- 每个功能条目只使用一句话描述，并明确标注复选框状态。
- 如果无法用一句话准确描述某项功能，应在 `docs/` 下新增或更新一份聚焦该功能的文档，并在 `feature.md` 的对应条目中添加链接。
- 只有在实现及相关测试均完成后，才能将功能标记为已完成。`feature.md` 仅记录功能状态，不记录发布和线上验证状态。
- 待办功能统一记录在 `feature.md` 中。

## 6. 开发过程与提交规范

- 一个 Commit 只表达一个变更意图，并且可以独立评审、验证和回退；实现及其测试、必要文档可以一同提交，不同变更意图必须拆分。
- 开发依赖前置重构时，必须在技术方案阶段对齐重构的必要性、范围、风险和顺序；先提交行为不变的重构，再提交功能。实施中扩大重构范围时必须重新对齐。
- 每个 Commit 必须保持代码可构建并通过相关检查，提交说明应准确表达目的，且不得夹带无关改动。
- AI 只有在用户当前请求中明确要求推送时才能执行 Git 推送。改动必须先推送到功能或修复分支，再通过 Merge Request（MR）合入 `main` 或 `master`；禁止直接向 `main` 或 `master` 推送。

## 7. 自动化测试套件

- 新功能必须新增测试，缺陷修复必须增加能够复现问题的回归测试。
- 测试至少覆盖核心成功路径、失败路径、边界条件和兼容路径。
- 禁止通过删除测试、弱化断言、跳过检查或反复重跑不稳定测试使 CI 通过。
- 测试套件必须可以一键执行，并具备超时、环境隔离、自动清理和失败诊断能力。

测试分为三级：

| 级别 | 执行时机 | 必须覆盖 |
| --- | --- | --- |
| 快速门禁 | 每次提交或合并请求 | 格式检查、静态检查、单元测试、构建 |
| 集成验收 | 涉及接口、数据库、缓存、消息或网络协议 | 集成测试、Docker E2E、异常和降级场景 |
| 性能验收 | 涉及热路径、并发、线程、队列、缓存或容量 | 吞吐、成功率、CPU、内存、队列、丢弃率、P95/P99 |

高风险变更必须保留测试报告、关键日志和性能对比结果，并能关联到具体 Commit SHA。

## 8. CI 与合并门禁

- 快速门禁未通过不得合并。
- 高风险变更未通过对应的集成或性能验收不得合并。
- **编码完成后，开发人员必须明确触发 AI 基于实际代码差异进行 Review**。AI 必须在 Review 结论中按严重程度列出问题，并明确影响的文件、模块、接口、配置、数据及上下游，自动测试的覆盖与执行结果，以及未验证项和兼容性、性能、数据、安全、发布等风险。没有自动测试时，必须说明原因、替代验证方式和残余风险。
- AI Review 发现的问题必须修复后重新 Review，或**由开发人员明确记录不修复的原因和残余风险**。AI Review 不能替代非作者人工评审。
- CI 未执行的检查必须在合并请求中写明原因、**人工验证结果**和残余风险。
- 不得关闭、绕过或降低已有检查标准。
- **所有生产代码至少由一名非作者评审后才能合并。**

**以下变更必须由模块负责人复核：**

- 权限、资金和用户数据；
- 数据库结构及数据修复；
- 公共接口、协议和兼容逻辑；
- 生产配置和依赖升级；
- 并发、数据面、缓存和核心选路逻辑。

## 9. 数据、配置和代码安全

- DDL、数据脚本与应用发布必须分开执行，并提供执行前检查和执行后校验 SQL。
- 数据库变更必须兼容新旧版本，禁止在同次发布中直接删除旧版本仍可能使用的字段。
- 批量数据操作必须支持预览、限量、幂等和中断恢复，**执行前必须人工批准**。
- 新功能开关默认关闭；配置缺失或非法时必须有明确、安全的默认行为。
- 外部调用必须设置超时，重试必须有次数上限；非幂等操作不得自动重试。
- 队列、缓存、连接、并发、批次和单轮工作量必须设置明确上限。
- 禁止忽略错误、使用空错误捕获或在失败后静默继续。
- 密码、Token、私钥、生产连接串和真实用户数据不得写入代码、日志、测试文件或测试报告。

## 10. 可观测性

核心流程上线前必须具备：

- 可通过请求标识或业务标识关联的结构化日志；
- 成功、失败、耗时、降级、队列和容量指标；
- 对应的告警和线上观察入口。

日志必须脱敏。监控标签必须使用固定、低基数字段，禁止使用用户 ID、连接 ID 或动态错误文本等高基数数据作为标签。

## 11. 发布制品与 Tag 管理

- 生产发布必须使用 Git Tag 触发 CI 构建的制品。
- 禁止发布本地或手工编译的二进制、镜像及其他制品。
- Tag 必须基于已合入主分支且通过全部发布门禁的提交创建。
- **创建 Tag 前，发布人员必须确认主分支已同步、工作区干净，且目标提交与远端主分支一致。**
- 发布制品必须记录 Tag、Commit SHA、构建时间和 CI Pipeline ID。
- 同一 Tag 对应的制品禁止覆盖或重新构建；需要修复时必须创建新 Tag。
- 发布前必须核对制品版本与目标 Tag、Commit SHA 完全一致。
- 分支流水线只用于验证，不产生可上线制品；Tag 流水线产生唯一可发布制品。
- 部署系统只能选择 Tag 制品，禁止上传本地文件或使用 `latest` 等可变标签。
- 回滚必须使用历史 Tag 对应的原始制品，禁止现场重新编译旧代码。
- 紧急发布也不得绕过 Tag 和 CI 构建流程。

## 12. 灰度、回滚与线上验证

高风险功能必须具备开关或等效的快速回退能力，并按以下顺序发布：

```text
自动测试 -> 测试环境 -> 白名单 -> 小流量灰度 -> 逐级放量 -> 全量
```

- 推荐灰度比例为 `1% -> 5% -> 10% -> 30% -> 50% -> 100%`。
- 每次放量至少等待一个配置刷新和监控观察周期。
- **发布前必须明确发布人、观察人、回滚负责人、观察指标、停止条件和回滚步骤。**
- 错误率、延迟、资源使用或业务指标超过预设阈值时，**发布或回滚负责人必须确认停止放量或立即回滚**。
- 发布后必须执行核心链路冒烟测试，并检查错误日志、告警及核心指标；**观察人必须确认验证结果**。
- 完成线上验证后才能宣布发布完成。

## 13. 高风险操作

**以下操作必须获得负责人明确批准，AI 不得自行执行：**

- **删除或批量修改生产数据；**
- **执行数据库迁移或数据修复；**
- **修改认证、权限、支付和计费逻辑；**
- **修改生产配置、密钥或访问策略；**
- **发布、回滚或操作线上服务；**
- **强制推送或重写共享分支历史。**

## 14. 事故处理

- **线上事故必须由人决定并负责止损**，再定位和修复。
- 事故处理过程必须记录操作人、时间线、影响范围、止损措施和恢复结果。
- 事故结束后必须复盘根因，并将防复发措施落实为自动测试、CI 门禁、监控告警或本规范中的明确规则。
